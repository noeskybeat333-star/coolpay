# CoolPay — контекст проекта для Claude Code

## О проекте

Инфраструктура интернет-магазина электроники. Развёрнута на выделенной VM,
приложение магазина — Laravel + Filament.

**Цель проекта:** CRM как центральная точка, где хранится вся информация по
всем каналам продаж — собственная витрина плюс маркетплейсы.

## Окружение

- Гипервизор: Proxmox VE
- VM: `shop-infra`
- ОС: Debian 13
- IP: `10.10.10.20`

## Репозиторий и пути

- Корень git-репозитория: `/opt/infra`
- Приложение магазина: `/opt/infra/apps/shop` (владелец `ruslan`)
- `/opt/infra/compose` — тоже `ruslan` (владение выровнено 13.08.2026)
- GitHub: `noeskybeat333-star/coolpay`
- Постоянные данные (вне репозитория): `/opt/data`, `/opt/backups`, `/opt/logs`

## Стек

- Laravel `13.20.0`
- Filament `5.7.1`
- PostgreSQL
- Docker Compose: `shop-app` (php-fpm), `shop-web` (nginx),
  `shop-scheduler` (`schedule:work`), `shop-queue` (`queue:work`)
- Очередь: драйвер `database`, таблица `jobs`

Типовая команда для artisan-команд в контейнере:
```bash
cd /opt/infra/apps/shop
docker exec --user "$(id -u):$(id -g)" --env HOME=/tmp shop-app php artisan <command>
```

**Не использовать `--env HOME=/tmp` для `tinker`** — psysh не сможет писать
конфиг и молча выпадет в bash. Для разовых проверок надёжнее одноразовый
php-скрипт в корне приложения, поднимающий Laravel через `bootstrap/app.php`.

## Что уже реализовано

### Витрина
Главная страница, каталог активных товаров, поиск, фильтрация по категориям,
цены и остатки, страницы товаров, описание/характеристики WB, светлая и тёмная
темы, баннеры, галерея изображений (полноэкранный просмотр, свайпы на мобильных).

### Интеграция Wildberries (каталог)
Импорт карточек WB: изображения, описание, характеристики, цены, остатки FBS,
связывание карточки WB с локальным товаром, отображение в Filament.

### Корзина (гостевая, через сессию)
```
app/Http/Controllers/CartController.php
app/Services/CartService.php
resources/views/store/cart.blade.php
```
Маршруты: `GET /cart`, `POST /cart/items/{product}`, `PATCH /cart/items/{product}`,
`DELETE /cart/items/{product}`.

В сессии хранится только ID товара и количество — цена всегда читается из БД
заново при открытии корзины (защита от устаревшей цены/неактивного товара/
превышения остатка).

### Оформление заказа
```
app/Http/Controllers/CheckoutController.php
app/Http/Requests/StoreOrderRequest.php
resources/views/store/checkout.blade.php
resources/views/store/order-success.blade.php
```
Маршруты: `GET /checkout`, `POST /checkout`, `GET /checkout/success`.

Логика внутри транзакции PostgreSQL: повторное чтение товаров →
`lockForUpdate()` → проверка публикации/цены/остатка → фиксация snapshot
в `order_items` → создание заказа → уменьшение остатка → очистка корзины.
Номер заказа: `CP-YYYYMMDD-NNNNNN`.

### Filament: управление заказами
```
app/Filament/Resources/Orders/
```
`CreateOrder.php`, `EditOrder.php`, `OrderForm.php` намеренно удалены — заказ
может появиться только через витрину или импорт маркетплейса, не вручную.

### Статусы и безопасная отмена
```
app/Services/OrderStatusService.php
```
Статусы заказа: `new, confirmed, processing, shipped, completed, cancelled`.
Статусы оплаты: `pending, paid, failed, refunded`.
`orders.stock_restored_at` — защита от повторного возврата остатка при отмене.

### Импорт заказов маркетплейсов — РАБОТАЕТ
```
app/Integrations/Contracts/ImportsMarketplaceOrders.php
app/Integrations/Results/OrderImportResult.php
app/Services/MarketplaceOrderUpserter.php     общий upsert для всех площадок
app/Services/WildberriesOrderImporter.php     разбор ответов WB
app/Services/MarketplaceOrderSyncRunner.php   блокировка, журнал, запуск
app/Console/Commands/ImportMarketplaceOrders.php
tests/Feature/WildberriesOrderImportTest.php  6 тестов
```

Цепочка: `WB API → WildberriesOrderImporter → MarketplaceOrderUpserter →
orders + order_items`. Всё знание про Wildberries живёт в импортёре; upserter
про площадки ничего не знает и переиспользуется для Ozon и остальных.

Импортёр WB обходит три модели работы, поэтому в тестах **`Http::fake`
обязан иметь ветку `'*'`**: незаявленные запросы запрещены, и без неё DBS
с DBW падают с ошибкой, подмешивая `failed` в результат про FBS.

Номера: свой `CP-YYYYMMDD-NNNNNN` сквозной для всех каналов, номер площадки
лежит в `external_number` и показывается описанием под номером CRM — иначе
заказ невозможно сверить с кабинетом. Для WB это идентификатор сборочного
задания, тот же, что в колонке «Заказ» кабинета.

### Импорты выполняются ТОЛЬКО в очереди

Это архитектурное решение, а не деталь. Раньше импорт шёл синхронно внутри
HTTP-запроса, и любой сбой на середине терял всю работу: лимит частоты WB
(`429`) на вспомогательном запросе цен убивал импорт целиком.

```
app/Jobs/SyncMarketplaceCatalog.php
app/Jobs/SyncMarketplacePrices.php
app/Jobs/SyncMarketplaceOrders.php
app/Services/MarketplaceCatalogSyncRunner.php
app/Services/MarketplacePriceSyncRunner.php
app/Services/MarketplaceOrderSyncRunner.php
app/Services/MarketplaceCooldown.php
app/Integrations/Exceptions/MarketplaceRateLimitException.php
app/Console/Commands/MarketplaceStatus.php
tests/Feature/MarketplaceCooldownTest.php     3 теста
tests/Feature/WildberriesCatalogImportTest.php  2 теста
```

Кнопки в Filament и команды `marketplace:import-catalog`,
`marketplace:import-prices`, `marketplace:import-orders` только ставят задачу
в очередь. Планировщик — тоже. Синхронный прогон остался лишь как отладочный
флаг `--sync`.

Джобы: 8 попыток, паузы 120/600/1800 с, `ShouldBeUnique` по кабинету.
При `429` драйвер бросает `MarketplaceRateLimitException`, джоба ловит его
и делает `release()` с паузой — попытка не расходуется, работа не считается
проваленной. Все прочие ошибки идут в журнал как есть.

Результат виден в админке: «Маркетплейсы» → «Журнал синхронизаций»
(`MarketplaceSyncLogResource`, автообновление раз в 15 с). Статусы:
`running`, `success`, `failed`, `retrying`. Операции: `catalog_import`,
`prices_import`, `orders_import`.

Проверено на живом кабинете 15.08.2026: при отказе API цен импорт каталога
сохранил 117 карточек и поставил отдельную задачу на цены — вместо прежнего
полного отката и восьми повторов подряд.

**Не возвращать импорты в синхронный режим.** Если нужен быстрый прогон —
`--sync` в консоли, но не в интерфейсе.

Проверено на живом кабинете: 6 заказов FBS, суммы сошлись с кабинетом WB
до копейки, отменённый заказ распознан, повторный прогон даёт
`создано: 0, обновлено: 6`.

## Яндекс Маркет API — измеренные факты

Проверено на живом кабинете 15.08.2026. База —
`api.partner.market.yandex.ru`.

- **Авторизация — заголовок `Api-Key`.** Вариант `Authorization: Bearer`
  отвечает `403 "OAuth token is invalid"`. Старая схема с OAuth и
  `campaign_id` в схеме учётных данных устарела, в сидере оставлен
  один API-ключ.
- **Два идентификатора.** `businessId` — кабинет целиком, к нему привязан
  каталог. `campaignId` — отдельный магазин, к нему привязаны заказы.
  Оба отдаёт `GET /campaigns`, спрашивать у человека не нужно: проверка
  подключения сохраняет их в `settings` подключения.
- **Одно подключение на бизнес, а не на кампанию.** Каталог общий, и
  четыре подключения означали бы четыре копии карточек. Заказы
  собираются со всех кампаний, модель работы (FBS/DBS) пишется в
  `fulfillment_type`, `campaign_id` — в `metadata`.
- **Лимиты щедрые и разные по ресурсам:** заказы 10000 запросов в час,
  каталог 100. Никакой машинерии с паузами, как у WB, не требуется.
- **`price` в заказе — это то, что заплатил покупатель, а не выручка
  продавца.** Разницу Маркет компенсирует баллами, она лежит в
  `subsidies`. Проверено на двух заказах: 134715 + 65285 = 200000 и
  127040 + 52960 = 180000, второе совпало с «Итого» в кабинете.
  `unit_price` = `price` + субсидия; раскладка сохраняется в
  `product_snapshot`. Без этого выручка занижена на всю скидку Маркета.
- **`priceBeforeDiscount` и `basicPrice.discountBase` — зачёркнутые
  витринные цены**, вдвое-втрое выше реальных. В расчётах не участвуют,
  хранятся как `old_price`.
- Цены **в рублях**, а не в копейках. Валюта приходит как `RUR` —
  устаревший код рубля, нормализуется в `RUB`.
- Даты в формате `d-m-Y H:i:s`.
- Статус двухуровневый: `status` + `substatus`. Отмена с
  `USER_NOT_PAID` — это `unpaid`, а не `refunded`: возвращать нечего.
- **`limit` и `page_token` идут в query-строке.** В теле запроса
  `offer-mappings` их молча игнорирует и всегда отдаёт 50 записей.
- `offerId` карточки — артикул продавца, поэтому связь с товаром CRM
  прямая, по совпадению артикула.
- Остатков каталог не отдаёт, нужен отдельный запрос по кампании.
  `stocks_read` честно выставлен в `false`, статус выводится из
  `campaigns[].status` (`NO_STOCKS`, `DISABLED_BY_PARTNER`).

### Устаревшие карточки

`external_id` карточки — это `offerId`. Переименование артикула на
площадке создаёт новую карточку, а старая остаётся навсегда. Поэтому
после **полного** обхода каталога всё, что не обновилось в этом проходе,
помечается `status = 'archived'`. Удалять нельзя: на карточки ссылаются
заказы. Архивировать после оборванного импорта тоже нельзя — «непришедшие»
там означают лишь «не дошли», а не «удалены».

## Wildberries API — намеренные факты, не догадки

Всё ниже проверено запросами к живому кабинету 12.08.2026. Не переоткрывать.

### Заказы FBS: `GET marketplace-api.wildberries.ru/api/v3/orders`

- **Глубина строго 90 дней.** `dateFrom` за 90 дней отдаёт данные, за 120 и
  больше — `HTTP 200` с пустым списком, без ошибки. Отсюда
  `WildberriesOrderImporter::MAX_DEPTH_DAYS = 90`.
- **`dateTo` поддерживается и обязателен для DBS/DBW.** Прежняя запись здесь
  утверждала обратное — она была ошибочной: 400 приходил не из-за самого
  `dateTo`, а из-за периода шире 30 дней. Исправлено 16.08.2026 по
  документации `dev.wildberries.ru/docs/openapi/orders-dbs`.
- **Максимум 30 календарных дней на запрос** — ограничение API, а не наше.
  Поэтому глубина режется на окна в `fetchWindows()`. Число окон считается
  от глубины, **округлённой до дней**: `$since` вычисляется на доли секунды
  раньше, чем `now()` внутри цикла, и период ровно в 30 дней иначе давал
  второе окно шириной в миллисекунды — лишний запрос на каждую модель.
- **Окно скользит.** Заказ старше 90 дней исчезает из выдачи навсегда. Поэтому
  ежечасная автосинхронизация обязательна, а не желательна. На момент первого
  импорта самый старый заказ был возрастом 89 дней — сутки до потери.
- **`next` не обнуляется** даже на неполной странице, признаком конца выборки
  служить не может. Останавливаться по короткой странице или повторению курсора.
- **Цены в копейках.** `price`/`convertedPrice` делить на 100.
- **Одна запись = одна единица товара**, поля количества нет. Несколько единиц
  приходят отдельными сборочными заданиями с общим `orderUid`.
- **Данных покупателя нет** — ни имени, ни телефона, `address: null`. Ради этого
  и делались nullable поля в `orders`.
- **Статусов в ответе нет.** Отдельный `POST /api/v3/orders/status`
  с `{"orders":[id,...]}` → `supplierStatus` + `wbStatus`.

### Лимиты запросов — ГЛОБАЛЬНЫЕ на весь кабинет

Снято с заголовков ответа `429` 13.08.2026:

```
X-Ratelimit-Limit: 1
X-Ratelimit-Retry: 380
X-Ratelimit-Reset: 380
detail: "Limited by global limiter, per seller <uuid>"
```

- **Счётчик общий на кабинет, а не на эндпоинт.** Запросы каталога, цен,
  остатков, заказов и статистики расходуют один бюджет. Притормаживать
  надо все обращения к WB, а не только «шумный» метод.
- **Паузу брать из `X-Ratelimit-Retry`** (секунды), а не угадывать. Наши
  зашитые 120 с оказались втрое короче нужных 380, и каждая преждевременная
  попытка попадала в тот же счётчик, продлевая блокировку — повторы сами
  себя и душили. Это делает `MarketplaceRateLimitException::fromResponse()`,
  добавляя 20 с запаса.
- **Штраф растёт экспоненциально.** Замер 13.08.2026 за один вечер:
  380 → 432 → 918 → **3581** секунды. Каждый запрос во время блокировки
  продлевает её, поэтому «попробовать разок, вдруг отпустило» — худшее,
  что можно сделать.
- **`MarketplaceCooldown` — общий рубильник на кабинет.** Раз лимитер
  глобальный, паузу обязаны соблюдать все операции, а не только та, что
  получила отказ. Оба runner'а проверяют паузу до похода в API и объявляют
  её при `429`; команда `marketplace:import-orders` во время паузы даже не
  ставит задачу в очередь. Без этого задача каталога ждала свои 900 с,
  а планировщик заказов в это же время спокойно долбил тот же API.
- **Один отказ — не повод отменять всё.** Карточки живут в `content-api`,
  цены в `discounts-prices-api`, остатки и заказы в `marketplace-api`.
  Пока импорт каталога был единой операцией, отказ по ценам выбрасывал и
  уже полученные карточки, а каждый из восьми повторов выкачивал их
  заново — и грел общий лимитер данными, которые давно дошли. Теперь
  `importCatalog` сохраняет карточки, ставит флаг `pricesDeferred` и
  отдаёт задачу `SyncMarketplacePrices`, которая ходит **только** по
  сохранённым карточкам (`raw_data` содержит всё нужное, включая
  `chrtID`). Content API она не трогает вовсе.
- **Не ходить за остальным после `429`.** Если цены отказали, за
  остатками драйвер уже не идёт: лимитер общий, и этот запрос лишь
  продлил бы блокировку.
- **Отложенные цены не подменяем нулями.** Когда цены не доехали,
  `price`, `stock_quantity` и `status` не пишутся совсем (колонки
  nullable). Записать `0` и `no_price` означало бы показать в CRM
  выдуманные данные из-за чужого лимита частоты — для системы, которая
  задумана как единая точка правды, это хуже пустого поля.
- В `fetchPrices` стоит `usleep(700000)` перед запросом, в цикле карточек —
  `usleep(650000)` между страницами. Не убирать.
- Statistics API лимитирован отдельно и жёстче: примерно один запрос
  в минуту на метод.
- **Лимит на API цен обходится размером порции, а не расписанием.**
  `/api/v2/list/goods/filter` принимает до 1000 товаров за запрос, а мы
  просили по 100 — механически повторив размер страницы пагинации
  карточек. На 117 карточек уходило два запроса, и при одном разрешённом
  запросе в 15 минут обновление цен не могло завершиться в принципе.
  С `PRICES_CHUNK = 1000` весь каталог обновляется одним запросом.
  Проверено 16.08.2026: «Обработано карточек: 117, обновлено: 117».
  Задумываться о постраничности — когда каталог перевалит за 1000.
  Мораль: прежде чем строить машинерию вокруг лимита, проверить,
  нельзя ли просто сделать меньше запросов.
- **Ограничение на API цен аномальное, но именно на нём.** Карточки
  (`content-api`) и заказы (`marketplace-api`) ходят свободно —
  импорт 117 карточек проходит за секунды. Формулировка WB
  «Limited by global limiter, per seller» вводит в заблуждение: она
  звучит как лимит на продавца, а ведёт себя как лимит на эндпоинт.
  Кабинет выключать не нужно, работает всё, кроме обновления цен.
- **16.08.2026: ограничение постоянное, и отказы продлевают окно.**
  Сутки без единого запроса ничего не изменили — версия про
  накопленный штраф опровергнута. Хуже того: приходя ровно к моменту
  открытия окна, мы получаем отказ с полными ~900 с, то есть
  **отказанный запрос перезапускает отсчёт**. Отсюда и «эскалация»
  380 → 432 → 918 → 3581 от 13.08: это были не растущие штрафы, а
  наши собственные повторы, каждый раз сдвигавшие границу.
  Практические следствия: не проверять «отпустило ли» вручную;
  не держать задачи WB в очереди — автоповторы делают ровно то же
  самое и вредят; ждать заметно дольше, чем просит заголовок.
  Пока не решено — **не трогать API Wildberries вообще**.
  Открытый вопрос в поддержку WB, requestId
  `27a91ea99830a4ee06d865e398458583`, 16.08.2026 09:02:26 UTC.
- **15.08.2026 кабинет ушёл в режим «один запрос на 15 минут».**
  Измерено: успешный запрос вернул `X-Ratelimit-Remaining: 0`, а
  следующий — `429` с `retry`, ровно доводящим до 900 секунд от первого.
  Прежние 898 объяснялись тем же: импорт делал первый запрос (склады),
  а второй (цены) попадал уже в пустой бюджет.
  Следствие: **`importPrices` не может завершиться в принципе** — ему
  нужно минимум два запроса. Пока лимит такой, импорт WB нерабочий.
  Токен при этом в порядке: одиночный запрос к API цен отвечает `200`,
  категория «Цены и скидки» у токена есть. Причина ограничения не
  выяснена — либо накопленный штраф, либо ограничение на аккаунт;
  requestId для поддержки: `8e51a2919634f7a1f46b39d6bcdc651b`.

### Маппинг статусов

| `wbStatus` | наш `status` | `payment_status` |
|---|---|---|
| `sold` | `completed` | `paid` |
| `canceled`, `canceled_by_client`, `declined_by_client`, `defect` | `cancelled` | `refunded` |
| прочее | по `supplierStatus` | `pending` |

| `supplierStatus` | наш `status` |
|---|---|
| `new` | `new` |
| `confirm` | `confirmed` |

- `external_id` заказа = `orderUid` (группирующий).
- `external_number` = минимальный `id` сборочного задания — именно он виден
  в колонке «Заказ» в кабинете WB.
- ID всех заданий группы → `order_items.product_snapshot.external_line_ids`
  и `orders.metadata.assembly_task_ids`.
- Товар: `nmId` → `MarketplaceListing.external_id` → `product_id`.
  Запасной путь — `article` против `seller_sku`/`offer_id`.

### Другие модели работы — DBS и DBW ВКЛЮЧЕНЫ 16.08.2026

Продавец работает **не только по FBS**. В кабинете три вкладки: Маркетплейс
(FBS), Витрина (DBS), Курьером (DBW). Все три включены в
`WildberriesOrderImporter::SOURCES`.

Пока была включена только FBS, картина была ложной: 6 заказов за май-июнь
и «продаж больше нет». На деле в DBS лежало 162 заказа, свежий от 10.08.
Вывод на будущее: **отключённый источник выглядит как отсутствие данных**.

- `GET /api/v3/dbs/orders` — все четыре параметра `limit`, `next`,
  `dateFrom`, `dateTo` **обязательны**. Метод называется «Get Information on
  Completed Orders»: отдаёт только завершённые — проданные и отменённые.
- `GET /api/v3/dbs/orders/new` отдаёт `HTTP 200` и пустой список: он про
  «новые прямо сейчас», а не про историю.
- **Пути статусов у моделей разные.** FBS: `POST /api/v3/orders/status`,
  поле `orders`, идентификатор в ответе `id`. DBS:
  `POST /api/marketplace/v3/dbs/orders/status/info`, поле `ordersIds`,
  идентификатор `orderId`. Прежняя схема «`<path>/status`» для DBS не
  работала. Пути заданы явно в `SOURCES`, не выводятся из пути списка.
- **Цена: `convertedFinalPrice` → `finalPrice` → `convertedPrice` →
  `price`.** У DBS есть цена после скидок, у FBS таких полей нет. Сверено
  с кабинетом: `11772000` → 117 720 ₽, `8840000` → 88 400 ₽. Перебор
  нужен именно перебором, а не `data_get` с умолчанием: поле может
  присутствовать со значением `null`.
- **Статусы DBS шире FBS.** `receive` — получен покупателем, это
  `completed`, а не `shipped`. `reject` (отказ при получении) и
  `cancel_missed_call` — отмены. Живой пример из кабинета:
  `supplierStatus: new` + `wbStatus: declined_by_client` — покупатель
  отказался в первый час; без правки заказ висел бы новым.
- **Ответ 4XX засчитывается за десять запросов.** Серия неудачных зондов
  выбивает burst и приводит к 429. Зонды по WB — с паузами.

### DBW: список и статусы найдены зондом

`GET /api/v3/dbw/orders` — параметры те же, что у DBS. Статусы:
`POST /api/v3/dbw/orders/status`, поле `orders`, ключ `id` — то есть форма
FBS под своим префиксом. Из трёх моделей по схеме FBS идут две, выбивается
только DBS со своим `/api/marketplace/...status/info` и `ordersIds`.
Угадать это по аналогии было нельзя: сначала я взял форму DBS и получил
`404 path not found`. Проверено зондом 16.08.2026 на живых заданиях.

Ловушка при поиске: `/api/v3/orders/status` (общий метод FBS) отвечает на
задания DBW **`HTTP 200` с пустым `orders`**. Зонд, смотревший только на
код ответа, принял это за рабочий путь и остановился, не проверив
остальных кандидатов. **Признак успеха для метода статусов — непустой
`orders`, а не HTTP 200.** Это общее правило для зондов по WB: у площадки
хватает эндпоинтов, отвечающих успехом на бессмысленный запрос.

Побочно из этой истории родилась защита, которую стоит сохранить: при
недоступных статусах импортёр **не передаёт `status` и `payment_status`
вовсе**, а `MarketplaceOrderUpserter` сохраняет уже известный статус.
Сбой метода статусов не откатывает выкупленный заказ в «новый».

### Statistics API — ДОСТУП ЕСТЬ, импортёр не написан

Токен с категорией «Статистика» выпущен 13.08.2026. Проверено:
`statistics-api.wildberries.ru/api/v1/supplier/orders` отдал 652 записи
за 400 дней (раньше отвечал `401 "token scope not allowed"`).

Это **единственный путь** к полной истории и к FBO — оперативный API дальше
90 дней не отдаёт ничего.

Что ещё НЕ проверено на живых данных и требует зонда перед написанием
разбора (правило «факты, а не догадки»):

- какое поле цены соответствует уже импортированному `convertedPrice/100`

Лимит у Statistics API отдельный и жёстче: примерно один запрос в минуту

## Известные проблемы инфраструктуры

### Сборка ассетов — НАЛАЖЕНА 16.08.2026

```bash
cd /opt/infra/compose/shop && docker compose --profile tools run --rm assets
```

Сервис `assets` в compose — `node:22-bookworm-slim` под профилем `tools`,
поэтому вместе со стеком не поднимается. Монтирует тот же каталог, что и
php-fpm, и кладёт результат на хост: собирать внутрь образа бессмысленно,
bind-mount всё равно перекроет. Пишет от `1000:1000` — иначе `public/build`
достаётся root и следующая сборка упирается в права.

Запускать **после правок в CSS, JS и шаблонах админки**: Tailwind собирает
классы статически, новый класс попадёт в CSS только после пересборки.

Два условия, без которых это не работало:

- **Своя тема Filament** (`resources/css/filament/admin/theme.css`,
  подключена через `->viteTheme()`). Без неё панель грузит готовый CSS
  Filament, и классы из `app/Filament` и `resources/views/filament` в него
  не попадают вообще — сколько ни пересобирай. Директивы `@source` в теме
  указывают Tailwind, где искать. Файл создан вручную по
  `vendor/filament/filament/stubs/ThemeCss.stub`: `make:filament-theme`
  требует Node внутри php-контейнера, а его там нет.
  Откат при поломке — убрать строку `viteTheme()` и `optimize:clear`.
- **Шрифты локальные.** Плагин `bunny()` ходил за ними на
  `fonts.bunny.net` во время сборки, и сборка падала по таймауту.
  Файлы лежат в `resources/fonts`, `@font-face` объявлен в `app.css`,
  директива `@fonts` из шаблонов убрана. Сборка стала офлайновой.

Остаётся неприятность, но не проблема: `Dockerfile` тратит время на
`composer install`, результат которого маунт перекрывает. `vendor/`
живёт на хосте. Переносить код внутрь образа сейчас не стоит — это
сломает работу «правлю на хосте, вижу сразу». Вернуться к этому при
упаковке стека в продукт для чужих серверов.

### DNS в контейнерах
Docker формирует `/etc/resolv.conf` контейнера **в момент создания**. При
загрузке VM контейнеры с `restart: unless-stopped` стартуют раньше, чем dhcpcd
запишет DNS, и получают пустой список апстримов — тогда любые обращения к
внешним API падают с `cURL error 6: Could not resolve host`.

Симптом: в `docker exec <c> cat /etc/resolv.conf` вместо `# ExtServers: [...]`
написано `NO EXTERNAL NAMESERVERS DEFINED`.
Лечение: `docker compose up -d --force-recreate` для затронутого стека.
Постоянное решение (не сделано): прописать `dns` в `/etc/docker/daemon.json`.

### Прочее
- HTTPS не настроен: в `compose/caddy/Caddyfile` только `:80` без домена.
- `docs/network.md` расходится с реальностью: LAN описан как `10.10.10.0/24`,
  а DHCP раздаёт DNS из `172.16.250.0/24`.

## Как работать с этим проектом (правила для Claude Code)

- **Пользователь выполняет команды сам.** Давать точную команду и объяснять,
  что она делает и что искать в выводе, а не запускать за него. Читать
  исходники проекта — можно и нужно, это контекст для объяснений.
- **Не ломать существующее.** Корзина, оформление заказа, Filament-ресурс
  заказов, статусы, импорт заказов — рабочий функционал. Изменения только
  точечные и с пониманием, зачем.
- **Способ оплаты через маркетплейс НЕ добавлять** на сайт — пользователь
  явно исключил этот вариант. Выплаты маркетплейсов продавцу — отдельный
  будущий финансовый модуль, не способ оплаты заказа.
- **Цены и остатки НИКОГДА не уходят на маркетплейс сами.** Раздел «Цены»
  правит только локальные таблицы; кода на запись в API нет, и это осознанно.
  Токен WB при этом выпущен с правом записи — значит единственная защита
  здесь дисциплина, а не отсутствие прав. Когда дойдёт до отправки цен:
  1) включение только по явному флагу на конкретной карточке, по умолчанию
  выключено; 2) только ручное действие с подтверждением и показом
  «было → станет»; 3) сначала обкатка на ОДНОМ товаре и проверка результата
  в кабинете WB; 4) массовое применение — только после этой проверки;
  5) никакого запуска записи по расписанию; 6) каждая отправка пишется
  в `marketplace_sync_logs`. Нарушать этот порядок нельзя даже «для теста».
- **Заказы создаются только через витрину или импорт** — не восстанавливать
  `CreateOrder`/`EditOrder`/`OrderForm` в Filament, это удалено намеренно.
- **Транзакционность и `lockForUpdate()`** в оформлении заказа — не убирать,
  это защита от гонки при последней единице товара.
- **Snapshot данных в `order_items`** обязателен: история заказа не должна
  зависеть от текущего состояния товара.
- **Для заказов маркетплейсов остаток не возвращается при отмене** — это
  осознанное решение, не «баг».
- **Проверять фактами, а не догадками.** Перед тем как писать разбор ответа
  внешнего API — получить один реальный ответ и посмотреть на поля. Этот
  подход уже сэкономил здесь несколько переделок.
- **После правки PHP-кода перезапускать воркер и планировщик.**
  `queue:work` и `schedule:work` — долгоживущие процессы: классы
  загружаются один раз при старте и держатся в памяти, изменения файлов
  на диске они не видят. `shop-app` (php-fpm) перечитывает код сам,
  поэтому в браузере правка видна сразу, а в очереди — нет.
  ```bash
  cd /opt/infra/compose/shop && docker compose restart queue scheduler
  ```
  Симптом забытого перезапуска коварен: код исправлен, поведение старое.
  Ловится сверкой — например, в журнале синхронизаций видно сообщение
  в старой формулировке, без внесённых правок.
- **В кэш класть только скаляры и массивы.** В `config/cache.php` стоит
  `'serializable_classes' => false`: восстанавливать объекты из кэша
  запрещено, чтобы подменённое значение в хранилище не превращалось в
  экземпляр произвольного класса. Сохранённый объект вернётся как
  `__PHP_Incomplete_Class`, и проверка `instanceof` молча отдаст `null`.
  Так `MarketplaceCooldown` хранил `CarbonImmutable` и **бесшумно терял
  все паузы** — запись в базе была, а `secondsLeft()` возвращал 0.
  Ловится тестом `MarketplaceCooldownTest`; заметить это в тестах
  «записали — прочитали» нельзя, потому что тестовый драйвер `array`
  держит значения в памяти как есть.
- **`queue:clear` — только вместе с `cache:clear`.** Задачи с
  `ShouldBeUnique` держат замок в кэше (при драйвере `database` — в
  таблице `cache_locks`). `queue:clear` вычищает `jobs`, но про замки не
  знает, и кабинет остаётся заблокирован на `uniqueFor` (у нас час).
  Симптом: нажатие кнопки не создаёт задачу и не даёт ошибки — Laravel
  молча выбрасывает дубликат. Диагностика — посмотреть `cache_locks`.
- **После правок в шаблонах админки пересобирать ассеты.** Tailwind
  собирает CSS статически: класса, которого не было в исходниках на
  момент сборки, в готовом файле нет, и он молча не работает. Симптом —
  вёрстка выглядит так, будто стилей нет вовсе.
  `docker compose --profile tools run --rm assets`
- **`php -l` не ловит ошибок классов Filament.** Он проверяет только
  грамматику. Несуществующий класс, несовместимая сигнатура метода,
  конфликт свойства с трейтом, константа трейта — всё это видно лишь
  при загрузке классов. После правок в Filament запускать
  `artisan test` или хотя бы `artisan about`, а экраны открывать
  глазами: тестами они не покрыты.
- **Размеры внутри чужой разметки считать измерением, а не CSS.**
  Растяжка через `height: 100%` требует, чтобы вся цепочка контейнеров
  Filament была растянута; промах в одном звене ломает всё, а имена
  классов меняются между версиями. На дашборде высота холста графика
  вычисляется по фактическим координатам (`getBoundingClientRect`) —
  три попытки сделать то же правилами CSS провалились.
- Перед любой новой миграцией — `artisan migrate:status`.
- Все artisan-команды — через `docker exec` в `shop-app`, не на хосте.
- Отлаживать импорты удобнее командами, а не кнопками: у
  `marketplace:import-catalog`, `marketplace:import-prices` и
  `marketplace:import-orders` есть флаг `--sync`, который выполняет
  импорт прямо в терминале и печатает настоящую причину отказа.
  `marketplace:status` показывает паузу кабинета, последнюю
  синхронизацию и глубину очереди, не делая ни одного запроса к API.
